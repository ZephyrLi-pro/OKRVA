# 按自然分句流式播报

2026-10-30：修正“音频队列不断供，但听起来在词语中间停顿”的问题。

旧实现会在 4/12 个字、定时器超时或合成预算耗尽时切块。每次独立 TTS 都有终止语调和头尾静音，因此滚动缓存即使充足，拼起来也会在没有标点的位置停顿。单看播放器队列无法验证语言韵律。

## 当前规则

- 句号、问号、感叹号、分号和换行可结束完整语句；较长分句可以在逗号结束。顿号留在同一个分句内，避免枚举内容逐项重新起声。
- 未闭合的语句不再因字数或定时器被强行派发。小数、版本号、域名、文件扩展名中的英文点不会当作句号。
- 合成预算只决定合并几个完整分句，不能继续把一个分句切断。最终全文一次到达的路径也按自然分句预合成。
- 保留滚动缓存：快输入约 1.5 秒，中等约 6 秒，慢输入约 10 秒的音频前缀；随后边播边补，短回答结束时释放已有前缀。不是必须等待全文。
- 局部 WAV 只裁掉接近数字静音的头尾（10 毫秒帧、全声道峰值不超过 16/32768），保留开头 60 毫秒、逗号尾部 120 毫秒、其他结尾 250 毫秒的保护量。全静音包不裁成负长度或空数组；不改变语速、音高、模型和音色。
- 取消、错误、历史、窗口、FIFO 及 9 秒追问保护继续启用。已有 CPUWeight=400 配置保持不变。

自然分段意味着尚未生成到合适标点的半句话要继续等待；不会为抢先出声而读成零碎的词组。

## 验证

完整 Qt 回归使用真实 MainWindow、私有 HTTP 和 SDL dummy：验证三句已生成内容及时排队，短句和长分句不被截断，700 毫秒过去后未闭合语句仍不合成，标点到达后完整派发；覆盖版本号、扩展名、最终全文路径、取消、历史和追问。

边缘静音裁剪测试保留了幅值仅 24/32768 的整段轻声测试数据，只缩短两端静音；全静音输入也保持有效。

| 方式 | TTS 请求数 | 非标点分段处 | 音频总长 |
| --- | ---: | ---: | ---: |
| 旧碎片模式 | 13 | 12 | 25.472 秒 |
| 自然分句，未裁边缘 | 3 | 0 | 16.192 秒 |
| 自然分句，产品同款边缘处理 | 3 | 0 | 14.532 秒 |

旧碎片拼接处的 WAV 自带约 0.77–0.83 秒低能量空白，和网络或播放队列是否缺数据无关。对照中旧追踪漏掉的纯标点尾块被附到最后一块，保证两边输入文字完全一致。裁剪样例由调用产品同一 C++ 函数的小程序生成，保存在 `punctuation-trimmed.wav`；它是测试样例，不是预设的助手回答。

正式 PPT 第 12 页链路的同一 73 字回答，TTS 实际请求长度为 26 / 33 / 14 字，非末段均在逗号结束。相对语音软件接口提交问题：141.09 秒起播，150.63 秒全文生成完成，155.54 秒播放结束。缓存起播音频 11.434 秒，开播比全文完成早约 9.54 秒，播放阶段约 14.45 秒；没有重建出的音频供给空档，9 秒追问返回 `ready:8753`。这是一轮 1.7B 冷启动阅读测试，初始等待仍长，不代表普通聊天的等待时间。
